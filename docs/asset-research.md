## What backs the representations, and how an exit differs from a DEX sale

**WETH:** Wormhole's Wrapped Token Transfers documentation describes locking the origin asset and issuing a corresponding destination representation backed 1:1; it explicitly illustrates ETH on Ethereum becoming WETH on Solana [9]. Redemption across chains reverses the bridge accounting. The SDK's exact 8-decimal Solana WETH entry is preferable to assuming Ethereum's 18 decimals [2]. A Solana DEX sale back into USDC does not itself redeem the bridge claim or prove the Ethereum reserves. Wormhole contracts, Guardians and operational controls are separate risks from the market price of ETH.

**HYPE:** Sunrise explicitly labels this listing **Wormhole NTT**, rather than a generic Wormhole Token Bridge wrapper [3]. Its security page explains that each listing's framework can differ: NTT can use source burns and destination mints, or a locking hub and minting spokes; token ownership and upgrades remain part of the asset's control model [4]. The public table lists HYPE mint authority `3X46pk5u5gLfppNRyPF5PcKyuHYrA2pHnyJK5HRLPzfi` and metadata update authority `NGoD1yTeq5KaURrZo7MnCTFzTA4g62ygakJCnzMLCfm` [3]. Do not treat a non-null mint authority as a failed bridge identity check: a bridge needs controlled minting, so match the documented authority and its program instead. Sunrise's withdrawal guide says HYPE sent back to HyperEVM is automatically unwrapped into its native gas token [5]. That is a documented mechanism, not an independently tested redemption in this task.

**ZEC:** Sunrise's 2026-10-16 announcement says its ZEC rollout is powered by NEAR Intents, with an adjacent official reply giving the full Solana mint [6]. The Sunrise static listed-assets table fetched today stops at June-era listings and does **not** contain ZEC. Its absence there must not be misrepresented as a positive table match. Exact identity was therefore independently resolved through the live NEAR bridge contract [7]. NEAR's own Omni Bridge overview identifies Zcash verification as light-client plus Chain Signatures, and Solana as Wormhole plus Chain Signatures; the general architecture uses an MPC signing network and a coordinating bridge contract [8]. The bridge registry maps the Solana token to `zec.omft.near`; that binds the representation to the NEAR bridge token and does not independently audit all native ZEC reserves, Zcash redemption availability, or shielded recipient support. Never call this a native shielded ZEC balance.

**SOL:** Classic WSOL is SOL held in a Token Program account, with the token amount synchronized to lamports above the rent reserve [1]. For this bot's ordinary Solana swaps, classic WSOL is the intended Jupiter SOL mint. There is also a separate Token Extension Program native mint in the current Solana docs; do not substitute it merely because its label is WSOL.

## Counter-review: issues found and resolved or left open

1. **Ticker/name is insufficient.** Search returns unrelated pump.fun ZEC and HYPE coins. Rejected all symbol-only matches. Only exact primary-source mints enter the identity allowlist.
2. **Sunrise does not imply every asset uses NTT.** Its own current documentation is framework-agnostic. HYPE is NTT; ZEC's observed binding is Omni Bridge / NEAR Intents. Calling both the same NTT implementation would be incorrect.
3. **Documentation is not current chain state.** The HYPE table includes authority values; the static table omits ZEC. The parent must compare actual Solana owner program, decimals and authorities, including any Token-2022 transfer fees, hooks, delegates or other extensions.
4. **An authentic asset can still lack an economic route for a tiny order.** A price display or large aggregate volume does not establish that a sub-dollar buy and subsequent sale cover spread, LP fees, platform fees, priority fee and account rent. Require exact-size Jupiter quotes in both directions, simulation and actual confirmation.
5. **Unrealized marks are not realized profits.** Native SOL reserved for fees and recoverable token-account rent must be accounted consistently; inbound funding is capital, not profit. No 5–10% gain can be inferred from these identity findings.

## Execution boundary for the parent

`verified-assets.json` is a research identity allowlist, **not an execution approval file**. Before any swap, independently fetch all mint accounts through Helius, compare programs/decimals/authorities, obtain buy and sell quotes for the exact intended size, inspect all instructions, retain adequate fee SOL, simulate and verify confirmed token/lamport deltas. Do not bridge merely to buy these exposures: the investigated use case is a Solana DEX swap, so origin-chain bridge minimums and gas are not immediate execution requirements. Origin bridge risk still affects the held assets.
